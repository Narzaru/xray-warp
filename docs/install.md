# Установка

Установщик рассчитан на отдельный Linux-хост с systemd, локальным Docker Engine и доступом root. Он может перезапустить Docker, изменить sysctl/firewall и пересоздать контейнеры. Для рабочего VPS используйте [сверку состояния](server-state.md) и [инструкцию обслуживания](operations.md). Запуск setup для просмотра или для применения ночной заявки не требуется.

## Сеть и ОС

| Внешняя сеть хоста | DNS домена | Профиль для новой установки | Что доступно |
|---|---|---|---|
| Только IPv4 | A | `HOST_NETWORK=ipv4` | IPv4 bridge. Direct, второй VPS с доступным входом или WARP |
| Только IPv6 | AAAA | `HOST_NETWORK=ipv6` | IPv6 у контейнеров и внутренний IPv4 для SSH/панели. Direct к IPv6 либо второй VPS с достижимым входом. WARP этого проекта требует внешний IPv4 |
| IPv4 и IPv6 | A, AAAA или оба по нужным адресам | `HOST_NETWORK=dual` | У контейнеров доступны оба семейства при маршрутизации на хосте. WARP/Hev всё равно выходит по IPv4 |

По умолчанию `auto` проверяет маршруты обеих семей в ядре. Если у работающего проекта уже есть IPv4 bridge и у хоста есть маршрут IPv4, он сохраняется. Менять семейство существующей сети нужно отдельно, в окно обслуживания. Внешний вход по IPv6 и IPv6-выход из контейнера — разные возможности. Например, при IPv4 bridge Docker может принимать входящий IPv6 через userland-proxy.

**IPv6-only не означает доступ ко всему IPv4-интернету.** Нужны DNS и маршрут до реестров образов, ACME и остальных источников; для IPv4-only сервисов потребуется отдельный достижимый выход или NAT64/DNS64 для совместимых приложений. NAT64 не превращает этот WARP-профиль в поддерживаемый IPv6-вариант. Для [IPv6 в пользовательском bridge Docker](https://docs.docker.com/engine/network/drivers/bridge/#use-ipv6-in-a-user-defined-bridge-network) установщик требует Engine 27+.

Проверки зависят от возможностей хоста, а не от номера дистрибутива:

- Linux с systemd, работающим cron/crond с `/etc/cron.d`, Bash, GNU coreutils, util-linux (`flock`, `setsid`), Python 3, curl, iproute2, sysctl и gettext (`envsubst`). Ядро должно предоставлять BBR; для WARP нужен WireGuard, для выбранных образов — совместимая архитектура.
- Локальный rootful Docker Engine и `docker compose` с поддержкой `configs.content`, `pull --ignore-buildable` и `up --pull never`. Устаревший Python `docker-compose` v1 не подходит. При установке из репозитория Docker используйте его [инструкцию для Ubuntu](https://docs.docker.com/engine/install/ubuntu/) или [Debian](https://docs.docker.com/engine/install/debian/); не смешивайте пакеты из двух источников.
- Рабочий VPS — Ubuntu 26.04.1. Для Debian/Ubuntu подготовьте также `gettext-base curl iproute2 procps util-linux cron`. На системах с crond названия пакетов отличаются. Не проверялись установка на каждом дистрибутиве, SELinux enforcing, rootless Docker, OpenRC и системы без обычного IPv4 loopback. Не отключайте SELinux или firewall для обхода проверки.
- Хостовой sshd должен быть достижим из bridge по `host-gateway` на `SSH_PORT`. До проверки SSH через 443 сохраните доступ к консоли хостера. Если настроен firewalld или внешний firewall, разрешите необходимые потоки вручную.

## Переменные

Из этой версии checkout (включая `config/`, `tools/` и нужные Compose-файлы):

```bash
cd /opt/x-ui
install -m 600 .env.example .env    # только на новой установке
nano .env
sudo bash setup-3xui.sh
```

Файл `.env` читается Bash и Compose. Используйте доверенный файл с присваиваниями. При подготовке из Windows сохраняйте скрипты с LF.

| Переменная | Значение |
|---|---|
| `DOMAIN`, `EMAIL` | Публичное имя сертификата и контакт ACME |
| `SSH_PORT` | Реальный порт sshd на хосте, обычно 22. Порты 80/tcp и 443/tcp заняты фронтом и не подходят для sshd |
| `HOST_NETWORK` | `auto`, `ipv4`, `ipv6`, `dual` |
| `PROXY_MODE` | `off` (по умолчанию), `warp`, `vps`. [Как настроить сам Xray](outbound.md) |
| `WARP_SOCKS` | `auto`: для новой установки Hev, для известного существующего образа сохраняется его вариант. Явно: `hev` (TCP/UDP) или `microsocks` (TCP) |
| `VPS_ADDRESS`, `VPS_PORT`, `VPS_UUID`, `VPS_SNI` | Для `vps`: адрес, порт (обычно 443), UUID и имя TLS второго сервера |
| `HYSTERIA`, `HYSTERIA_PASSWORD` | `off` или `on`; если пароль не задан, при включении генерируется. У этого входа отдельный выход и политика. [Hysteria2](hysteria.md) |
| `TIMEZONE` | Часовой пояс панели, по умолчанию системный. Таймер GeoIP/GeoSite использует собственное расписание |

### Проверка DNS

Нужна хотя бы одна публичная запись A или AAAA. Установщик сверяет **все** ответы с адресами хоста, для IPv4 учитывает также внешний адрес за NAT. Ошибка резолвера не считается отсутствием записи. При первой выдаче сертификата несовпадение останавливает установку; если сертификат уже существует, выводится предупреждение. При осознанной нестандартной схеме можно запустить `sudo env SKIP_DNS_CHECK=1 bash setup-3xui.sh`; это не обходит проверку владения доменом в ACME. [Let's Encrypt сначала проверяет IPv6](https://letsencrypt.org/docs/ipv6-support/): рабочая A-запись не компенсирует чужой HTTP-ответ по AAAA.

## Что выполняет скрипт

1. Проверяет режим, зависимости, локальный Docker, сеть, Compose и совместимость с существующей установкой. При ожидающем bootstrap, исключении или незавершённой транзакции geodata останавливается до изменений Docker. Проверяет, что выбранный профиль не исключает существующий сервис. Если действующее задание cron несовместимо, сохраняет вариант `.candidate` для сравнения.
2. Готовит каталоги, настройки Docker и ядра, конфиги Caddy и опциональной Hysteria. Изменение `daemon.json` может повлиять и на другие контейнеры хоста.
3. Если сертификата ещё нет, использует ACME HTTP-01 на 80/tcp: существующий Caddy или временный nginx; Certbot читает тот же webroot. При существующем сертификате повторная выдача пропускается.
4. Поднимает выбранный набор контейнеров. Для нового Hev при отсутствии локального образа выполняется сборка; при повторном запуске готовый образ сохраняется. Проверяет фронт и передачу SSH, устанавливает задания cron для нового хоста. При интерактивном запуске журнал — `setup.log`.
5. **После установки:** через [панель](panel.md) создать inbound и клиента, задать policy и при необходимости WARP/VPS-маршруты. БД панели, блокировки РФ, механизм обновления geodata и частное исключение рабочего VPS не переносятся на новый хост автоматически.

## Фаервол

У провайдера откройте 80/tcp и 443/tcp на каждом опубликованном семействе. Только для Hysteria также нужен 443/udp. Не публикуйте 2053, 10000, 8443 или 1080. Если установлен UFW, скрипт добавляет правила для публичных портов и доступ от интерфейса bridge проекта к порту sshd; сам UFW не включает. Docker меняет правила фильтрации при публикации портов — [ограничения интеграции с firewall](https://docs.docker.com/engine/install/ubuntu/#firewall-limitations). Работа сайта по одной семье не подтверждает его доступность по второй.

## SSL-сертификат

Постоянный Certbot проверяет продление каждые 12 часов. Cron отдельно перечитывает файлы сертификата: `docker exec caddy caddy reload --force --config /etc/caddy/Caddyfile`. Без `--force` неизменившийся текст Caddyfile может оставить в памяти прежний сертификат. При включённой Hysteria её нужно перезапустить для чтения нового сертификата. Xray в этой схеме принимает h2c и сертификат не читает. Особенность уже развёрнутого entrypoint Certbot описана в [сверке VPS](server-state.md).
