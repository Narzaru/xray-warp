# Сеть: мобильные каналы, таймауты, диагностика

Почему на Wi-Fi всё летает, а на мобильном интернете тот же профиль еле шевелится, и почему долгие соединения рвутся.

## Режимы xHTTP

| Режим | Соединений | Когда выбирать |
|---|---|---|
| `packet-up` | много коротких | канал без потерь; единственный режим, переживающий nginx впереди |
| `stream-up` | download и upload раздельно | компромисс |
| `stream-one` | одно долгоживущее | дорогое установление соединения (CGNAT, DPI) — **по умолчанию** |

Режим задаёт **клиент**; на сервере достаточно `mode: auto` — он принимает любой.

В `stream-one` каждое TCP-соединение приложения становится отдельным HTTP/2-запросом `POST /game/` внутри общей трубы: тело запроса — аплинк, тело ответа — даунлинк.

```
TCP+TLS до сервера (одно, с xmux — 2-3)
 └─ HTTP/2
     ├─ stream 1: POST /game/  ← браузер → youtube.com
     ├─ stream 3: POST /game/  ← Claude Code → api.anthropic.com
     └─ ...
```

## xmux

`enableXmux: true` в панели только **разрешает** мультиплексирование, параметры задаёт клиент. На дефолтах весь трафик едет по одной трубе, и одна потеря блокирует всю очередь за собой — head-of-line blocking на уровне TCP, затем HTTP/2. На канале с потерями это роняет скорость в разы.

Лечится явным числом соединений (`xui-link.py` кладёт его и в ссылку, и в JSON):

```json
"xhttpSettings": {
  "extra": {
    "xPaddingBytes": "100-1000",
    "xmux": { "maxConnections": "2-3", "maxConcurrency": 0 }
  },
  "host": "yourdomain.com",
  "mode": "stream-one",
  "path": "/game"
}
```

- Больше 2-3 не ставьте: по отчётам сообщества (2026) ТСПУ замораживает на ~120 с серию из 3+ TLS-рукопожатий к одному хосту за десятки миллисекунд, особенно для подсетей хостеров вроде Hetzner.
- `maxConnections` и `maxConcurrency` взаимоисключающие: задавая первое, второе обнуляют.
- Настройки xhttp живут **внутри `extra`**, не отдельным полем.
- Глобальный **Mux** (mux.cool) в клиенте должен быть **выключен**: он складывает потоки обратно в одно соединение.

## Таймауты простоя

Долгие «молчащие» соединения — SSE у LLM-API во время долгого thinking, YouTube с заполненным буфером — рвут два независимых таймаута. Сняты должны быть оба.

### Caddy: read_body_idle / write_idle

С версии 2.11 Caddy по умолчанию сбрасывает запрос, по которому **60 секунд** не шли данные (`read_body_idle 1m`, `write_idle 1m` — защита от slowloris). Считается только аплинк: пока приложение отправило запрос и молча ждёт ответ, тело `POST /game/` стоит, и через минуту Caddy сбрасывает этот поток. Соседние потоки в той же трубе живут — поэтому обрывы избирательные.

Симптомы:

- `API Error: Connection lost mid-response` у Claude Code и других LLM-клиентов на длинных ответах;
- видео перестаёт грузиться, пока не перезагрузишь страницу;
- в `docker logs caddy` массово `aborting with incomplete response ... "error": "reading: i/o timeout"`.

В `config/caddy/Caddyfile` оба таймаута подняты до 30 минут (0 задать нельзя — он означает «по умолчанию»). Применить на работающем сервере без разрыва соединений:

```bash
export $(grep ^DOMAIN= .env)
envsubst '${DOMAIN}' < config/caddy/Caddyfile > Caddyfile
docker exec caddy caddy reload --config /etc/caddy/Caddyfile
```

> Образ `caddy:2-alpine` обновляется cron'ом каждую неделю, поэтому такие смены дефолтов приезжают сами. Если после воскресенья что-то сломалось — первым делом `docker logs caddy`.

Проверка: через VPN запросить эндпоинт, который отдаёт заголовки и потом молчит пару минут, — ответ должен прийти целиком, а не оборваться на 60-й секунде.

### XRay: connIdle

По умолчанию XRay закрывает соединение, по которому 300 секунд не прошло ни байта. **Settings → Xray Configs → Advanced** — заменить блок `policy` на `config/xray/policy.json` (`connIdle: 1800`, stats-поля панели сохранены), затем **Restart XRay**. Делается при любом `PROXY_MODE`.

> У клиентов на Xray-core (v2rayNG и т.п.) действует тот же дефолт 300 с со своей стороны. Если обрывы на ~5 минутах остаются — поднять `connIdle` и в конфиге клиента.

## IPv6

Сеть `xray-net` создаётся без IPv6, поэтому XRay выходит в интернет только по IPv4 — даже если у хоста есть IPv6. Входящие подключения по IPv6 (при AAAA-записи) при этом работают: их принимает docker-proxy.

Для доменов это незаметно: Go получает «network unreachable» мгновенно и уходит на IPv4. Проблема — с IPv6-**адресами** назначения. Клиент с включённым IPv6 в TUN (и `routeOnly`, который оставляет исходный IP) шлёт в туннель соединения на IPv6-адреса, сервер не может их открыть, а приложение не откатывается на IPv4: TUN уже принял соединение локально. Сайты с IPv6 (Google, YouTube) висят до таймаута.

Поэтому в клиентах IPv6 выключается: в v2rayNG — **Настройки → Enable IPv6** выкл., в sing-box/Hiddify — IPv6 Mode = Disable / IPv4 only.

## Congestion control

Хостовой sysctl **не действует на контейнеры** — у каждого свой сетевой namespace. Поэтому BBR задан дважды: в `/etc/sysctl.d/99-vpn-tuning.conf` для хоста и в `sysctls:` каждого сервиса в `docker-compose.yml`. Критичен он для **sslh**, который терминирует внешнее TCP-соединение клиента.

```bash
for c in sslh caddy 3x-ui; do
    printf "%-8s " "$c"
    docker exec $c cat /proc/sys/net/ipv4/tcp_congestion_control
done
```

Cubic на канале с джиттером в сотни миллисекунд принимает скачок задержки за перегрузку и режет окно вдвое; BBR даёт кратный прирост.

## Диагностика TCP-соединений

Метрики живых клиентских соединений видны в namespace sslh:

```bash
PID=$(docker inspect -f '{{.State.Pid}}' sslh)
nsenter -t "$PID" -n ss -tin state established "( sport = :443 )"
```

- `bytes_retrans` против `bytes_sent` — доля ретрансмиссий; 15–20% означает потери в канале, настройкой сервера не исправить;
- `app_limited` — TCP простаивает, потому что приложение не подаёт данные: узкое место выше;
- `rtt` против `minrtt` — расхождение в разы указывает на bufferbloat у оператора;
- `bbr:(bw:...)` и `pacing_rate` — во что упёрся алгоритм.

## Чего не ждать

- Тест packet loss на speed.cloudflare.com через этот стек бессмыслен: он меряет потери через WebRTC поверх UDP, а UDP здесь инкапсулирован в TCP-туннель. Ориентируйтесь на скорость, latency и `ss`.
- Потолок TCP-транспорта на канале с реальными потерями не пробить: распараллеливание сглаживает, но не устраняет. Радикально помогает QUIC — [docs/hysteria.md](hysteria.md).
