# Сеть: мобильные каналы, таймауты, диагностика

Почему на Wi-Fi всё летает, а на мобильном интернете тот же профиль еле шевелится, и почему долгие соединения рвутся.

## Режимы xHTTP

| Режим | Соединений | Когда выбирать |
|---|---|---|
| `packet-up` | много коротких | канал без потерь; единственный режим, переживающий nginx впереди |
| `stream-up` | download и upload раздельно | компромисс |
| `stream-one` | двунаправленный поток в одном запросе | вариант для сравнения со `stream-up` |

Режим задаёт **клиент**; на сервере достаточно `mode: auto` — он принимает любой.
Генератор `xui-link.py` по умолчанию задаёт клиенту явный `stream-up`:
поведение клиентского `auto` зависит от версии ядра.

В `stream-one` каждое TCP-соединение приложения становится отдельным HTTP/2-запросом `POST /game/` внутри общей трубы: тело запроса — аплинк, тело ответа — даунлинк.

```
TCP+TLS до сервера (одно, с xmux — 2-3)
 └─ HTTP/2
     ├─ stream 1: POST /game/  ← браузер → youtube.com
     ├─ stream 3: POST /game/  ← Claude Code → api.anthropic.com
     └─ ...
```

## xmux

XMUX настраивается на клиенте. Поле панели `enableXmux` не является параметром
серверного Xray. Потоки внутри одного HTTP/2 TCP-соединения делят его потери
и задержки; несколько соединений могут уменьшить влияние этого ограничения.

Текущие настройки генератора (`xui-link.py` кладёт их и в ссылку, и в JSON):

```json
"xhttpSettings": {
  "extra": {
    "xPaddingBytes": "100-1000",
    "xmux": {
      "maxConnections": "2-3",
      "maxConcurrency": 0,
      "hMaxRequestTimes": "600-900",
      "hMaxReusableSecs": "1800-3000",
      "hKeepAlivePeriod": 0
    }
  },
  "host": "yourdomain.com",
  "mode": "stream-up",
  "path": "/game"
}
```

- `2-3` — выбранный для проекта лимит, а не универсальный порог для всех сетей.
- `maxConnections` и `maxConcurrency` взаимоисключающие: задавая первое, второе обнуляют.
- При наличии `extra` все параметры кроме `host`, `path`, `mode` берутся из него.
- Глобальный **Mux** (mux.cool) в клиенте должен быть **выключен**: он складывает потоки обратно в одно соединение.
- В проверенных ядрах встроенные умолчания xmux (`maxConnections 3`, `hMaxRequestTimes 600-900`, `hMaxReusableSecs 1800-3000`) подставляются, **только если все поля `xmux` нулевые** (`infra/conf/transport_method.go`). Если задать своё число соединений, лимиты переиспользования следует указать явно.
- `hMaxReusableSecs: "1800-3000"` — через 30–50 минут старое соединение перестаёт получать новые запросы. Текущие запросы продолжаются до завершения; ротация не переносит уже открытое видео на новое соединение. Ранее использовавшиеся `120-300` были экспериментальным диапазоном, а не общей рекомендацией разработчиков.
- `hKeepAlivePeriod: 0` выбирает стандартный интервал keepalive (H2: 45 с), а не отключает его. Отрицательное значение отключает keepalive. В генераторе интервал задаётся через `--keepalive`, ротация — через `--reusable-secs`.

### Проверка: клиент действительно держит 2-3 соединения

Ссылка с `extra` ещё не гарантирует, что клиент её применил: приложение может молча проигнорировать параметр. На практике (2026-10) клиенты с «правильной» ссылкой держали по 85–107 соединений и открывали новое каждые 1–2 секунды, иногда пачками по 4 штуки за 0,3 с. Это ровно тот триггер заморозки, описанный выше.

Симптом: YouTube или Instagram перестают грузиться и оживают только после перезапуска клиента. Причина: часть соединений заморожена (пакеты молча пропадают, RST не приходит), а клиент продолжает считать их живыми.

Число соединений на клиента. Внешний TCP терминирует sslh, поэтому смотреть нужно в его namespace:

```bash
P=$(docker inspect -f '{{.State.Pid}}' sslh)
nsenter -t $P -n ss -tnH state established '( sport = :443 )' | awk '{peer=$NF; sub(/:[0-9]+$/,"",peer); print peer}' | sort | uniq -c
```

Замороженные соединения видны по `backoff:` и `cwnd:1`:

```bash
nsenter -t $P -n ss -tniH state established '( sport = :443 )' | paste - - | grep -c backoff
nsenter -t $P -n nstat -az TcpExtTCPAbortOnTimeout   # сколько раз сервер так и не дождался клиента
```

Число соединений само по себе не доказывает сбой XMUX: при ротации старые
соединения с активными запросами могут оставаться открытыми. Если наблюдается
быстрый неконтролируемый рост числа соединений, нужно проверить как минимум:

- **Баг Xray-core v26.9.8 – v26.10.10** (сборки на Go 1.27, [XTLS/Xray-core#6797](https://github.com/XTLS/Xray-core/issues/6797)): пока TLS-рукопожатия висят, `maxConnections` не ограничивает число TCP-соединений. Клиент открывает новое на каждый запрос, вплоть до тысяч соединений. Эту версию ядра содержит v2rayNG 2.3.11. Лечится обновлением ядра в клиенте.
- Клиент не понимает `extra` в ссылке. Тогда импортируйте полный JSON из `xui-link.py`.

### Мёртвые соединения на сервере: tcp_retries2

Замороженный сокет со стороны сервера живёт, пока не закончатся повторы передачи. По умолчанию их 15, это около 15 минут. В `docker-compose.yml` для sslh стоит `net.ipv4.tcp_retries2=6`, с ним около минуты. Клиенту это не помогает, пакеты до него всё равно не доходят, но сервер перестаёт копить мусор. На работающем сервере применяется без перезапуска контейнера:

```bash
nsenter -t $(docker inspect -f '{{.State.Pid}}' sslh) -n sysctl -w net.ipv4.tcp_retries2=6
```

## Таймауты простоя

### sslh-select: обратный DNS в логировании

`sslh-select` обслуживает соединения одним циклом. Обратное разрешение
адреса для лога выполняется синхронно и при медленном DNS может задержать
все соединения; это отдельно отмечено в
[man page](https://github.com/yrutschle/sslh/blob/v2.3.1/sslh.pod#L159).
В inline-конфиге `sslh-cfg` задано `numeric: true;`: в логах остаются IP и
числовые порты, DNS для их форматирования не требуется. Это не изменяет
`resolve_on_forward: true` — имена `caddy` и `host.docker.internal` по-прежнему
разрешаются для выбора бэкенда на новых соединениях.

Для миграции старой конфигурации `tools/sslh-numeric.py` предусматривает проверку в изолированном контейнере, резервную копию и откат.
Пересоздаётся только sslh, поэтому SSH и VPN через 443 кратковременно
обрываются. После пересоздания проверьте SSH и HTTPS через порт 443.

Долгие «молчащие» соединения — SSE у LLM-API во время долгого thinking, YouTube с заполненным буфером — рвут два независимых таймаута. Сняты должны быть оба.

### Caddy: read_body_idle / write_idle

С версии 2.11 Caddy по умолчанию сбрасывает запрос, по которому **60 секунд** не шли данные (`read_body_idle 1m`, `write_idle 1m` — защита от slowloris). Считается только аплинк: пока приложение отправило запрос и молча ждёт ответ, тело `POST /game/` стоит, и через минуту Caddy сбрасывает этот поток. Соседние потоки в той же трубе живут — поэтому обрывы избирательные.

Симптомы:

- `API Error: Connection lost mid-response` у Claude Code и других LLM-клиентов на длинных ответах;
- видео перестаёт грузиться, пока не перезагрузишь страницу;
- в `docker logs caddy` массово `aborting with incomplete response ... "error": "reading: i/o timeout"`.

В `config/caddy/Caddyfile` оба таймаута подняты до 30 минут (0 задать нельзя — он означает «по умолчанию»). Применить на работающем сервере без разрыва соединений:

```bash
export $(grep ^DOMAIN= .env)
envsubst '${DOMAIN}' < config/caddy/Caddyfile > Caddyfile
docker exec caddy caddy reload --config /etc/caddy/Caddyfile
```

> Образ `caddy:2-alpine` обновляется cron'ом каждую неделю, поэтому такие смены дефолтов приезжают сами. Если после воскресенья что-то сломалось — первым делом `docker logs caddy`.

Проверка: через VPN запросить эндпоинт, который отдаёт заголовки и потом молчит пару минут, — ответ должен прийти целиком, а не оборваться на 60-й секунде.

### XRay: connIdle

По умолчанию XRay закрывает соединение, по которому 300 секунд не прошло ни байта. **Settings → Xray Configs → Advanced** — заменить блок `policy` на `config/xray/policy.json` (`connIdle: 1800`, stats-поля панели сохранены), затем **Restart XRay**. Делается при любом `PROXY_MODE`.

> У клиентов на Xray-core (v2rayNG и т.п.) действует тот же дефолт 300 с со своей стороны. Если обрывы на ~5 минутах остаются — поднять `connIdle` и в конфиге клиента.

## IPv6

Различайте три участка: адрес, по которому клиент подключается к VPS; адреса сети Docker; доступные адреса назначения у выбранного выхода. AAAA домена позволяет подключиться к фронту по IPv6, но сама по себе не даёт IPv6 клиентскому трафику. При IPv4 bridge и выходе MicroWARP/Hev доступность IPv6 на хосте сама по себе не даёт клиентам IPv6-выход.

На новой установке профили `ipv6` и `dual` подключают [IPv6 override](../docker-compose.ipv6.yml): контейнеры получают IPv6, а внутренняя IPv4-связность остаётся для панели и SSH. Для прямого выхода нужна маршрутизация у хостера; второй VPS определяет доступность адресов со своей стороны. Для текущего варианта WARP действует ограничение IPv4. Подробнее — [матрица установки](install.md).

Если TUN принимает IPv6 назначения при IPv4-выходе, подключение к IPv6-литералу не получает автоматического запасного IPv4. В таком профиле выключите IPv6 в **TUN клиента**. При подтверждённом IPv6-выходе это ограничение не требуется.

## Congestion control

Хостовой sysctl **не действует на контейнеры** — у каждого свой сетевой namespace. Поэтому BBR задан дважды: в `/etc/sysctl.d/99-vpn-tuning.conf` для хоста и в `sysctls:` каждого сервиса в `docker-compose.yml`. Критичен он для **sslh**, который терминирует внешнее TCP-соединение клиента.

```bash
for c in sslh caddy 3x-ui; do
    printf "%-8s " "$c"
    docker exec $c cat /proc/sys/net/ipv4/tcp_congestion_control
done
```

Cubic на канале с джиттером в сотни миллисекунд принимает скачок задержки за перегрузку и режет окно вдвое; BBR даёт кратный прирост.

## Диагностика TCP-соединений

Метрики живых клиентских соединений видны в namespace sslh:

```bash
PID=$(docker inspect -f '{{.State.Pid}}' sslh)
nsenter -t "$PID" -n ss -tin state established "( sport = :443 )"
```

- `bytes_retrans` против `bytes_sent` — доля ретрансмиссий; 15–20% означает потери в канале, настройкой сервера не исправить;
- `app_limited` — TCP простаивает, потому что приложение не подаёт данные: узкое место выше;
- `rtt` против `minrtt` — расхождение в разы указывает на bufferbloat у оператора;
- `bbr:(bw:...)` и `pacing_rate` — во что упёрся алгоритм.

## Чего не ждать

- Тест packet loss на speed.cloudflare.com через этот стек бессмыслен: он меряет потери через WebRTC поверх UDP, а UDP здесь инкапсулирован в TCP-туннель. Ориентируйтесь на скорость, latency и `ss`.
- Потолок TCP-транспорта на канале с реальными потерями не пробить: распараллеливание сглаживает, но не устраняет. Радикально помогает QUIC — [docs/hysteria.md](hysteria.md).
