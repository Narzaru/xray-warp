# Исходящий трафик Xray

`PROXY_MODE` выбирает инфраструктуру и подсказки установщика. Маршрут задаётся **отдельно в панели**. На новой установке без настройки выход определяется текущим шаблоном панели (обычно direct).

| Режим | Маршрут клиента |
|---|---|
| `off` | Прямой выход с IP хоста |
| `warp` | Xray → SOCKS5 `warp:1080` → WireGuard → Cloudflare |
| `vps` | Xray → VLESS/TCP/TLS на втором VPS; отдельного контейнера в этом стеке нет |

## Как применяются шаблоны

На новом хосте сначала сохраните исходный шаблон панели. [outbound-warp.json](../config/xray/outbound-warp.json) задаёт **поле outbounds**; для второго VPS установщик подставляет параметры в [шаблон outbound-vps](../config/xray/outbound-vps.json). В редакторе одного правила вставляется только объект правила с `outboundTag`, без оболочки `routing` или массива `rules`. Названия редакторов зависят от версии панели. Перед перезапуском проверьте результат: API-запись и блокировки должны остаться выше общего правила.

## PROXY_MODE=warp

Вариант Hev для новой установки поддерживает TCP и UDP; upstream MicroSOCKS обеспечивает только TCP. Оба используют SOCKS5 внутри Docker-сети и не публикуют порт 1080. Поставляемый профиль Hev использует IPv4 для выхода.

- Для обычного WARP последний маршрут — [routing-warp.json](../config/xray/routing-warp.json). Он **не включает блокировку РФ**.
- Для повторения рабочей политики используйте [routing-warp-ru.json](../config/xray/routing-warp-ru.json) как значение **всего** поля `routing`, либо перенесите его правила по одному, в том же порядке. Сначала сверьте тег своего клиентского inbound с указанным в файле. Нужны `IPOnDemand`, sniffing и базы с используемыми категориями. Не перезаписывайте другие пользовательские правила без сопоставления.
- Первый outbound — `warp-out`. Наличие `direct` и даже второго общего правила ниже WARP не обеспечивает автоматического резерва. [routing-direct.json](../config/xray/routing-direct.json) меняет политику только при явном переключении и раскрывает выходной IP хоста.
- [outbound-direct-ggc-fast-fail.json](../config/xray/outbound-direct-ggc-fast-fail.json) — исторический эксперимент для прямого выхода; его нет в рабочем шаблоне.

### Текущий вариант с UDP: MicroWARP + Hev

Локальный образ `local/microwarp-hev:0.3.1-hev2.13.1` добавляет в MicroWARP SOCKS5 с поддержкой UDP. При использовании шаблона `routing-warp-ru.json` российские назначения блокируются, остальной трафик клиентского входа выходит через WARP. `warp-out` — первый
outbound, общее правило WARP стоит после блокирующих правил; прямой резерв
пользовательскому трафику не назначен.

Сохраняются исходный MicroWARP, kernel WireGuard, регистрация, `warp-data`,
настройка маршрутов и штатный entrypoint. Вместо MicroSOCKS запускается
[Hev SOCKS5 Server](https://github.com/heiher/hev-socks5-server), поддерживающий
стандартные CONNECT и UDP ASSOCIATE. MASQUE/usque для этого не нужен.
Встроенный [MASQUE-режим MicroWARP](https://github.com/ccbkkb/MicroWARP#-wireguard-vs-masque)
тоже предлагает UDP через full `socks`, но использует пользовательский стек
и требует больше памяти.

Исходники образа — `config/warp/Dockerfile` и `microsocks-compat.sh`:

- база закреплена по digest используемого MicroWARP 0.3.1,
  `d5b709efd49dbec3a965c617eb263b46cdf1449e65776d1b9a351927439b2b17`;
- Hev 2.13.1 собирается статически из commit
  `404d8c3dfeedb561cc6135ee20a6ddbde74c3481` с закреплёнными подмодулями;
- адаптер принимает используемые entrypoint флаги `-i`, `-p`, `-u`, `-P`;
  анонимный режим требует `ALLOW_NO_AUTH=1`;
- исходящие сокеты привязаны к `wg0` и его IPv4, один worker;
- SOCKS UDP использует динамические relay-порты внутри Docker-сети.
  Публиковать `1080/udp` на хосте для связи с Xray в той же сети не требуется.

Сборка без переключения рабочего стека:

```bash
docker compose -f docker-compose.yml -f docker-compose.warp.yml \
  -f docker-compose.warp-udp.yml build warp
```

Для эксплуатации используются все три compose-файла. Updater учитывает
локальный образ: проверяет его ID, не загружает и не пересобирает его.
Недельный cron использует `pull --ignore-buildable` и `up --no-build --pull never`,
с общим lock для исключения пересечения с ручными изменениями.

```bash
docker compose -f docker-compose.yml -f docker-compose.warp.yml \
  -f docker-compose.warp-udp.yml up -d --no-build --pull never
```

Для отдельной проверки TCP и UDP используйте `tools/probe-warp-socks.py`. Для неё требуются адрес SOCKS-сервера, имя контейнера и путь к файлу результатов.

## PROXY_MODE=vps

Трафик уходит через второй сервер по VLESS/TCP/TLS:

```env
PROXY_MODE=vps
VPS_ADDRESS=1.2.3.4
VPS_PORT=443
VPS_UUID=xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx
VPS_SNI=yourexit.domain.com
```

Скрипт сгенерирует `outbound-config.json` с закрытыми правами — вставить в **Custom Config**, правило из `config/xray/routing-vps.json` последним после блокировок — в **Routing Rules**. Затем **Restart XRay**.

## Блокировка российских назначений на VPS

Шаблон `routing-warp-ru.json` задаёт дополнительную блокировку
для клиентского inbound `in-10000-tcp`: `geosite:category-ru` и `geoip:ru`
направляются в `blocked`. Доменное правило стоит перед правилами IP,
`routing.domainStrategy` — `IPOnDemand`. Sniffing этого inbound включён для
HTTP, TLS и QUIC с `routeOnly: true`: обнаруженное имя используется для
маршрутизации без подмены адреса назначения. Правило API остаётся первым.

Это дополнительная защита от российских запросов, попавших в туннель.
Российские сайты должны обходить VPN в маршрутизации клиента. При профиле
«всё через VPN» они перестанут открываться. Блокировка широкая: российский
IP блокируется независимо от страны владельца сайта. Покрытие доменов и
адресов зависит от установленных geodata.

### Точечное исключение для найденного видеокэша

Опциональное правило разрешает один кэш:
`full:rr2---sn-npcnxu-v8cs.googlevideo.com`, только inbound `in-10000-tcp`,
порт 443, TCP/UDP → `warp-out`. Manifest —
`config/xray/youtube-cache-exception.json`. В подготовленном кандидате правило идёт после API и запрета
`geoip:private`, но перед блокировками `geosite:category-ru` / `geoip:ru`.
Остальные российские назначения остаются заблокированы. Это явное изменение
политики для одного имени, а не исправление географической базы и не общее
разрешение `googlevideo.com` или IP, разделяемых несколькими сервисами.

Дневная команда `tools/update-geodata.py --queue-youtube-cache` готовит
кандидат, проверяет его штатным Xray в изолированном контейнере и сохраняет
`/opt/x-ui/pending-youtube-cache-exception.json`. Активная БД, сгенерированный
конфиг и работающий прокси при подготовке не изменяются. Ближайший ночной
job в 04:00 НСК применяет исключение в том же transaction и с тем же одним
restart/bootstrap `3x-ui`, что и geodata. Отдельного timer нет.

Меняется только `settings.xrayTemplateConfig` в постоянной БД панели, поэтому
перегенерация конфига и обновление контейнера сохраняют исключение. Операции
применения и отката используют compare-and-swap исходного значения; чужие
изменения шаблона не перезаписываются. Полная БД поверх свежих клиентов или
статистики при откате не восстанавливается. Ночное восстановление после
аварии возвращает также прежний шаблон. Approval удаляется только после
проверенного успеха; повтор не добавляет дубликат. Даже неизменившиеся
geodata не отменяют применение ожидающего одобренного правила.

Sniffing уже включает HTTP/TLS/QUIC с `routeOnly=true`, но наличие имени у
каждого UDP/XUDP потока пока не подтверждено. Проверка схемы и приоритетов
не доказывает доступность самого кэша. После ночной активации для проверки
нужен новый поток/сеанс QUIC, в котором сервер действительно видит это имя.
Дневные HTTP-пробы к YouTube для подготовки не выполняются.

Для новой установки перенесите в панель правила из `routing-warp-ru.json` и проверьте тег клиентского входа. Утилита `tools/block-ru.py` предназначена для миграции старого шаблона с прямым выходом.
